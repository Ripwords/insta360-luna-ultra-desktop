title: Contributing

Contributions are welcome. The short version: **open an issue first, then send a
pull request that references it.** The issue is where the "should we?" gets
settled; the PR is where the "how?" does. Splitting them keeps review focused
and means nobody writes code for a change that was never going to land.

## Open an issue first

Use the [issue templates](https://github.com/Ripwords/insta360-luna-ultra-desktop/issues/new/choose).

For a **bug**, the single most useful thing you can include is what the camera
was doing — its mode, whether a recording was running, and whether the app was
freshly connected or had been running a while. Most of this project's hard bugs
are state-dependent.

For a **feature**, say what you want to do with the camera, not which control you
think the app is missing. The camera's protocol has no published API, so what
looks like a small addition is sometimes unreachable and what looks large is
sometimes a single command.

## Then send a pull request

Reference the issue in the description (`Closes #123`). A PR without an issue is
fine for typos and docs fixes; anything touching camera behaviour should have one.

Before you push:

```bash
bun install
bun run test        # two vitest projects: node utils + Nuxt composables
bun run typecheck
bun run lint        # oxlint --deny-warnings — warnings are failures
```

A `pre-commit` hook runs `oxfmt` and `oxlint --fix` on staged files and re-stages
the results. Anything it cannot fix aborts the commit. **Never use
`git commit --no-verify`** unless the hook itself is broken.

Commits follow [Conventional Commits](https://www.conventionalcommits.org/) —
`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:`. The release
tooling derives the next version from them, so the prefix decides whether your
change ships as a patch or a minor.

## Rules that are not obvious from the code

### A camera feature is not done until the camera confirms it

::callout{icon="i-lucide-triangle-alert"}
The camera's failure mode is silent. It **accepts** a write, **echoes** it back
as successful, and **reads back** a value that a stale enum renders under the
wrong name. Nothing errors.
::

So a passing test proves nothing about a camera control. A feature ships only
once it has been set from the app and confirmed on the camera's own screen.
That is why [the feature map](/docs/feature-status) has a "built, gated off"
column — those controls are written and rendering, waiting on device
verification, not on code.

If you cannot verify on hardware, say so in the PR. A gated-off contribution is
still welcome; a contribution claiming verification it did not do is not.

### Camera access goes through the transport

Everything the UI needs from the camera is behind `CameraTransport`
(`app/utils/transport.ts`). The real TCP/HTTP implementation, `lunaClient`, is
imported by that one module and nowhere else.

```ts
// Wrong — and oxlint will fail the build
import { lunaClient } from "~/utils/lunaClient";

// Right
import { getCameraTransport } from "~/utils/transport";
const info = await getCameraTransport().connect(host);
```

This is enforced by a `no-restricted-imports` rule, not by convention. It exists
so tests and the documentation demo can substitute a fake camera — without it,
neither is possible.

### Two import rules that break the build

**Nothing reachable from a `*.worker.ts` may use a `~/` specifier.** Vite builds
workers in an isolated sub-build that resolves `~` against the wrong directory.
Use relative imports anywhere in a worker's dependency closure — see
`app/workers/watermark.worker.ts` and the modules it pulls in.

**The documentation site never edits files under `app/`.** The site at
`docs/site/` consumes the desktop app as a Nuxt layer, so it can reuse the real
components. If something needs to differ for the docs site, it is solved in
`docs/site/`, not by changing the app.

## Working on the app

```bash
bun run dev      # full desktop app (Tauri + Nuxt)
bun run ui:dev   # web frontend only — camera control unavailable
```

Camera control needs the desktop app; a browser cannot open a raw TCP socket.

You do not need the camera to work on most of the app. A mock server ships with
the repo:

```bash
node luna_mock_server/server.mjs \
  --root /path/to/media --host 127.0.0.1 --http-port 18080 --tcp-port 6666
```

Launch `bun run dev` and connect to `127.0.0.1:18080` from the Connect screen.
The mock covers connection, the media index, downloads and deletes. It does
**not** reproduce the per-function-mode settings storage, so settings read-back
still needs real hardware.

## Working on these docs

```bash
bun run docs:dev       # dev server
bun run docs:generate  # static build into docs/site/.output/public
```

Do not verify deploy-facing behaviour with `nuxt preview` — it runs a server that
GitHub Pages does not have. Serve `docs/site/.output/public` with a plain static
file server instead.
